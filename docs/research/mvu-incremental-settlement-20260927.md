# MVU 增量结算验证（2026-09-27）

## 改动

保留每楼变量快照和现有 journal 存储。优化模型提交指令之后的结算路径：

1. 事务变量、消息写入返回 v2 局部回执，携带事件 ID 和事务序号；重复回执忽略，缺失序号触发事件范围内完整重同步。
2. 执行器认领时协商浏览器基线，只同步变化楼层、目标楼层及必要的前置变量基线。旧客户端、基线缺失或不匹配仍使用完整上下文。保留 MVU 所需的消息别名和角色名称。
3. 服务端使用私有、限额的脱离存储缓存的读副本，按需复制被修改楼层。最终提交通过局部读和 CAS patch，将变量效果、待办清理、回执和 timeline 一起原子保存。冲突重试，旧存档或不支持局部操作时回退既有完整事务。

客户端事务执行期间推迟同生命周期的已提交上下文刷新，完成后再应用，避免覆盖运行中的变量草稿。草稿写入不发布为已提交更新。生命周期、分支、swipe、租约和效果校验保留。

`taskRun.commit({ messageIndices })` 是内部显式选择的局部提交接口：调用者须声明回调读取或修改的全部楼层；返回的 chat 只提供这些楼层和结算需要的头部字段，不包含历史回退点；未读取楼层不在投影中，不得作为完整存档使用。

## 本地浏览器测量

Chromium 加载官方 MVU，临时 journal 存档，每楼约 500 个嵌套字段，单份变量约 73 KB；固定指令将 hp 从 10 改为 9。初始化完成后开始计时，结束时实际保存并读回校验。无在线模型调用，无真实用户存档改动。

| 场景 | 提交至保存读回 | 结算模块 | 最终提交及读回 | 认领及两次写入回执 JSON |
| --- | ---: | ---: | ---: | ---: |
| 原始实现，400 楼 | 13.90 秒 | 11.85 秒 | 2.00 秒 | 180.70 MB |
| 优化后，400 楼 | 0.98 秒 | 0.81 秒 | 0.10 秒 | 1.367 MB |
| 优化后，800 楼 | 1.26 秒 | 0.96 秒 | 0.17 秒 | 1.371 MB |

MB 为未压缩 JSON 十进制字节。优化后的测试加入真实 background coordinator 的 pending/prepared 保存点和原子提交；原始测试使用完整存档提交，因此不是严格相同夹具的统计基准。以上是本机单次测量，不是延迟保证。800 楼存档约 61.46 MB。

初始化和首次完整上下文载入不计入此表，仍可能传输较大上下文；完整界面 Remote 传输、在线模型、其他卡片脚本及用户所述 1–5 分钟等待尚未在此测试中复现。不能据此认定所有慢结算均已解决。

本轮降低了大对象复制与传输量，尚未实现与楼层数无关的热路径：消息数组浅复制、完整性检查、turn 映射和差异遍历仍有 O(N) 成本；测量末尾还有完整存档读回。后续可维护楼层与有效变量基线索引、按 dirty floor 生成效果、按页管理浏览器消息缓存，并将验证改为局部读回。目标应为 O(本次读取和变更量)，不能对任意遍历历史的第三方脚本承诺常数时间。两次单点测量不足以确定增长曲线。

浏览器探针原始结果位于本地忽略目录 `output/playwright/mvu-settlement-probe/`（`run400atomic.txt`、`run800final.txt`）；夹具基于 `tests/fixtures/mvu-initialization-browser-smoke.mjs`。

## 第二轮：按修改集执行

后续改动把事务内部的消息数组改为 Map 支持的数组访问适配器：只分配、克隆被修改的楼层，不分配与总历史等长的数组。完整投影仍可显式逐楼读取；适配器只存在于内部事务，不能直接传给 structuredClone、IPC 或持久化接口。

效果生成使用事务已记录的 dirty floor 集合。声明楼层的最终提交使用同样的局部比较和应用过程；timeline 完成时只克隆选中楼层，局部读取及提交回执不复制历史 checkpoints。原有 checkpoints 仍完整保存在存档中，事务及磁盘重开测试校验它们未变化。

| 历史楼层数 | 原草稿创建及差异生成读取楼层次数 | 修改后 |
| --- | ---: | ---: |
| 20 | 40 | 3 |
| 400 | 800 | 3 |
| 10,000 | 20,000 | 3 |

`tests/mvu-bounded-work.test.mjs` 用访问计数测试真实工作副本、效果生成和 timeline 完成接口，不依赖机器速度。该测试也覆盖旧式全量投影、未声明楼层拒绝及失败时不发布部分修改。现有整合测试覆盖历史楼层修改、CAS 冲突和磁盘重开。

第二轮 Chromium 官方 MVU 400 楼单次验证通过：总计约 0.88 秒，结算模块约 0.72 秒，最终提交及完整读回约 0.10 秒，hp 磁盘值为 9。原始结果在本地忽略目录 `output/playwright/mvu-settlement-probe/run400bounded.txt`。这不是统计性能对比，不能把约 0.10 秒差值解释为稳定收益。

**复杂度边界：本轮仅证实事务草稿和按修改集执行阶段的楼层访问量不随历史长度增长，整个结算链路尚未达到 O(1)。** 存储层 `applyJsonChangesShared` 仍会复制消息数组，局部读取仍有完整性检查，运行时上下文仍有历史索引扫描和浏览器数组同步；冷读取、达到阈值的同步 journal snapshot 轮转也会处理完整存档。下一步需要分别改造存储内部的索引结构、前端缓存及独立快照维护，不能用本轮计数替代端到端证明。
