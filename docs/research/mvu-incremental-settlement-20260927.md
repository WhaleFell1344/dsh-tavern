# MVU 增量结算验证（2026-09-27）

## 改动

保留每楼变量快照和现有 journal 存储。优化模型提交指令之后的结算路径：

1. 事务变量、消息写入返回 v2 局部回执，携带事件 ID 和事务序号；重复回执忽略，缺失序号触发事件范围内完整重同步。
2. 执行器认领时协商浏览器基线，只同步变化楼层、目标楼层及必要的前置变量基线。旧客户端、基线缺失或不匹配仍使用完整上下文。保留 MVU 所需的消息别名和角色名称。
3. 服务端使用私有、限额的脱离存储缓存的读副本，按需复制被修改楼层。最终提交通过局部读和 CAS patch，将变量效果、待办清理、回执和 timeline 一起原子保存。冲突重试，旧存档或不支持局部操作时回退既有完整事务。

客户端事务执行期间推迟同生命周期的已提交上下文刷新，完成后再应用，避免覆盖运行中的变量草稿。草稿写入不发布为已提交更新。生命周期、分支、swipe、租约和效果校验保留。

`taskRun.commit({ messageIndices })` 是内部显式选择的局部提交接口：调用者须声明回调读取或修改的全部楼层；返回的 chat 只提供这些楼层和结算需要的头部字段，不包含历史回退点；未读取楼层不在投影中，不得作为完整存档使用。

本轮降低了大对象复制与传输量，尚未实现与楼层数无关的热路径：消息数组浅复制、完整性检查、turn 映射和差异遍历仍有 O(N) 成本；测量末尾还有完整存档读回。后续可维护楼层与有效变量基线索引、按 dirty floor 生成效果、按页管理浏览器消息缓存，并将验证改为局部读回。目标应为 O(本次读取和变更量)，不能对任意遍历历史的第三方脚本承诺常数时间。两次单点测量不足以确定增长曲线。

## 第二轮：按修改集执行

## 第三轮：索引化存储与浏览器缓存

存储和浏览器共用固定七层、每层 32 分支的持久化索引，覆盖 JavaScript 数组索引范围。正常局部更新仅复制目标位置的索引路径；完整性、有效 MVU 快照数量、缓存大小是索引聚合值，前一份有效变量快照通过索引定位。连续更新不累积覆盖链。这里的固定成本是相对于历史楼层数而言，读取或修改 K 楼仍为 O(K)，变量自身的字节数也影响成本。

结算输入按需分离所读取的楼层，保留旧版本视图及公共完整读取的深复制隔离。正常变量差异保留浏览器既有 turn 映射；楼层身份或布局发生变化时回退完整同步。浏览器变量回执仅更新命中的楼层，未修改的插件字段及未保存编辑不被访问或覆盖。

生产存储达到 journal 阈值时先封存已经持久化的日志，再交给独立 Worker 重放并压缩快照。快照完成后通过同一聊天的串行队列发布，不阻塞当前变量提交等待压缩。维护失败不撤销已经确认的写入；快照尚未生成以及生成失败时均可从 journal 恢复。退出时等待维护队列结束。首次存档、冷加载和完整快照本身仍是全量工作，只是周期性快照已移出前台提交路径。

### 尚未消除的非恒定工作

磁盘版本校验仍枚举并检查历史 journal/snapshot 文件，复杂度取决于文件数 J。曾试验文件监听缓存，但即时外部文件修改测试证明监听通知可能晚于下一次读取，因此撤回该方案，保留原有完整校验。不能为了常数时间而漏掉外部存档修改或损坏。

冷加载、结构变更、协议缺失后的完整重同步、完整界面上下文刷新，以及第三方脚本主动遍历历史仍可能为 O(N)。本轮没有改造事务结束时的完整界面刷新调度。后台快照仍消耗全量 CPU/I/O，且快照发布时的版本检查仍有 O(J) 工作。整个模型输出到界面完成链路尚不能承诺严格 O(1)。

## 第四轮：界面消息差异沿用到脚本沙箱

第三轮之后，服务端虽然不重复计算未修改消息的 hash，却仍遍历消息数组并重建全部 hash 表。浏览器接到局部消息后复制整个数组，再为脚本 iframe 克隆、装饰和发送完整上下文。这些操作现已改为：

1. 服务端每楼 hash 放入持久化索引，只读取 journal 声明的 dirty floor；游标各自保存独立索引版本，支持并发读取、淘汰和断线后的完整基线恢复。
2. 浏览器合并消息差异时复制固定深度索引路径，旧视图保持不变。头部及正文投影仍沿用既有协议。
3. 父页面对比共享索引分支，只装饰变更消息。发送给 iframe 的 committed 回执同样只包含变更消息；普通刷新及结算结束后延期应用的刷新均使用此路径。
4. 对比范围是当前草稿与最新已提交上下文之间的差异，包含需要恢复的临时草稿楼层。结算期间连续到达的刷新不会丢失较早修改，也不会把未提交变量留在界面里。

`tests/mvu-view-refresh-cost.test.mjs` 覆盖真实服务端差异生成、浏览器视图合并、父页面运行时及 iframe 接收函数。20、400、10,000 楼只改一楼时，服务端原先读取 20、400、10,000 楼，修改后均只读取一楼；浏览器合并及上下文刷新读取未修改历史载荷的次数为零。测试还覆盖两次延期刷新合并、临时草稿还原、普通后续刷新、旧视图隔离和生命周期切换后的完整同步。索引差异遍历也有固定访问量断言。

这里的“局部”指变更集合，包含历史编辑，不限定为最后一楼。楼层数改变、生命周期切换或缺少可信共享基线时仍走完整沙箱同步。此次测试运行实际客户端函数和 iframe bootstrap，但未新增完整浏览器界面延迟测量，也未验证所有 React 组件的渲染访问量。

最终完整回归：2,789 项通过、10 项跳过、0 失败；客户端生成一致性及 diff 检查通过。首次完整回归发现独立 RPC 测试未包含索引工厂，已将共享工厂移到首次使用处之前；另有一项生图等待窗口测试首次失败，最终完整复跑通过，未改动该测试或生图实现。

**剩余边界：这轮消除的是视图已经生成之后的消息同步成本，不代表服务端完整界面投影已经成为 O(K)。** `readViewDelta` 仍构造全量展示输入；`projectTavernHelperContext` 的 dirty 模式仍遍历楼层；`incrementalReplyView` 仍汇总、复制正文投影；状态回执、回退能力整理，以及正文投影/turn 映射的传输差异计算仍存在全量工作。它们需要分别维护派生索引及依赖失效规则。下一步应沿这些接口增加访问计数回归，不能只凭消息同步优化宣称端到端常数时间。

## 第五轮：变量结算复用上游派生投影

普通变量结算不会改变历史正文、消息身份或 turn，因此无需重新汇总这些投影。本轮在实际生产调用处接通以下路径：

- 正文缓存保存每楼展示输入的指纹。变量和 MVU 回执不参与静态正文投影，故只检查 dirty floor；展示输入未变化时直接复用不可变正文与静态面板结果，不再 flatten 历史、扫描静态状态栏来源、序列化整个缓存计量或深复制整份返回结果。默认公共调用仍返回可编辑的独立副本；只有生产视图调用显式选择共享不可变结果。
- Helper 完整投影建立消息索引；journal 证明楼层布局未变化时只更新 dirty floor，并复用原 turn 映射。`turn`、`role`、`greeting`、`tavernRole` 改变均使该证据失效。完整性检查使用索引聚合值。
- 回执使用固定深度索引分别定位最后一条 assistant、异常回执和普通回执。每次更新只重新投影变更楼层，读取时保留所有异常项及最近三条普通项。追加和截断直接更新索引；生命周期变化或缺少版本证据时重建。临时的 interrupted 状态在读取时覆盖，不污染缓存；同一 turn 重复出现时保留既有覆盖规则。
- 服务端传输层复用带内部不可变标记的 turn 映射 hash 和正文数组版本。没有该标记的可变对象仍重新检查，避免漏掉原地修改。游标只弱引用正文数组，不额外保留完整正文。
- `readViewDelta` 改为按访问楼层生成脱离存储的展示数据；未访问楼层不再预先复制。实时 EJS 渲染所需变量也按访问补入，普通静态路径无需先构造整份 renderChat 消息数组。

`tests/mvu-upstream-cost.test.mjs` 的 20、400、10,000 楼回归验证：仅改一楼的变量和回执时，正文、Helper、回执三个接口各自读取楼层数均低于固定上限 32；正文投影及 turn 映射保持同一不可变版本；随后的正文和 turn 传输 hash 不读取历史项。10,000 楼夹具显式使用 32 MiB 正文缓存预算，并检查确实命中缓存。生产正文缓存仍为 8 MiB、最多四个条目；新增输入指纹也计入容量，回执缓存另设总容量上限。

另有真实 journal 展示输入访问计数、外部修改不污染存储、回执异常保留、最近三条选择、重复 turn、重启中断显示、追加/截断及 turn 变化回退测试。既有正文编辑、分支和资源依赖变化测试继续对照完整投影，保证失效后的重建结果一致。

最终完整回归：2,798 项通过、10 项跳过、0 失败；新增上游测试 9 项通过。`node --check tavern-plugin/lib/index.js`、客户端生成一致性及 `git diff --check` 均通过。

**复杂度边界：上述结论适用于缓存命中且仅变量/回执变化的普通结算。** 正文或模板依赖变化时仍可能重新汇总完整正文；实时 EJS 可以依赖整个历史，不能把其执行视为常数时间。首次加载、缓存容量不足或失效、消息身份变化仍可触发完整重建。异常回执若有 R 条，保留并排序这些必要输出仍取决于 R。轻量会话输入、回退可用性检查和文件版本检查也还有历史相关工作；本轮不把整条 getSession 或整个界面渲染宣称为 O(1)，未新增端到端浏览器计时。

## 第六轮：轻量会话输入和回退显示结果

继续消除变量更新后的历史扫描：

- 会话注册表显式请求 scoped 轻量输入。journal 为消息的会话元数据维护固定深度索引，点提交只更新变更楼层；待结算 assistant 通过索引定位，无需反向扫描历史。读取按实际访问的楼层生成独立副本，历史变量不进入索引。默认 `readSessionState()` 仍返回普通数组，完整 `read()` 和旧存档 foreground-completed 迁移的完整数据契约不变。
- 元数据缓存总预算 8 MiB、最多八个会话，仅弱引用完整消息源；缓存失效、容量不足和成员增删走完整重建。旧读取结果保持自己的索引版本，调用方修改不污染缓存或存储；失败提交后的源版本不匹配会重建。
- 仅当原生宿主提供不可变事件快照、Surface 替换代数，且 journal 证明楼层布局未变时，复用回退/重生成按钮的派生显示结果。会话实例、事件快照、Surface 代数、楼层身份、救援导入和隐藏轮次等依赖变化都会失效。`importSource` 现在也使布局证据失效。撤销回退资格每次重新检查；真正执行回退继续走原有完整校验。旧宿主或缺少可信证据时不使用该缓存。

## 第十四轮：正文投影和剧情 turn 的渲染查询

继续审计正文渲染发现三处读放大：`tavernProjectionForTurn()` 反向扫描所有正文投影；组件每次用 reduce 计算最新投影 turn；`tavernStoryTurnForDshTurn()` 每次枚举全部重生成映射。现统一在接收不可变视图版本时建立派生查询，并沿真实增量维护。

## 第十五轮：空增量不再唤醒整批正文组件

实际刷新入口还有与已挂载楼层数相关的成本：空增量仍创建新的 view/helper/数组外壳，实时视图随后通知全部订阅者。即使所有内容相同，React 的外部存储快照身份变化仍导致一批组件刷新。

浏览器现在识别位置协议与按 turn 回执协议的真正空增量，保留原 view 对象，但照常推进游标和并发请求序号。已经建立索引的数组不重复包装。生产实时视图显式启用去重，只有 phase、view 身份和 error 都未改变时才跳过广播；内容改变、失败及恢复均正常发布。该模式下 updatedAt 表示最近一次发布的状态变化，不随无变化确认刷新；默认模块调用未开启时保留原发布行为。
