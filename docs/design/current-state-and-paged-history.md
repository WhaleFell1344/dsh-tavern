# 当前状态与按需历史：长档数据结构重构

日期：2026-09-27

状态：设计基线，用户已授权创建工作分支推进重构；本文不是全部已实现的说明。物理存储尚未选定，不以引入数据库为前提。

实施进展：已开始阶段 2/3 的独立文件 Adapter 原型，提供当前状态、不可变分页历史和原子小型入口。操作量、耗时、测试及接入前置项见 [第一阶段验证](../verification/conversation-page-store-20260927.md)。尚未迁移生产存档或替换主流程，物理存储仍未定为发布默认。

## 目标与证据

万轮决定存档体积，不应决定打开最后一页或继续一轮的工作量。普通打开读取当前状态和最近窗口；普通结算处理本轮状态变化，不构造完整 Chat。

现有实测见 [长档前台准备与并发冷读优化](../verification/long-history-header-performance-20260927.md)：67.4 MB 合成万轮存档，较早两轮发送至变量提交约 95–100 秒；最终复测浏览器打开至状态可见 44.395 秒，继续游玩超过 120 秒等待上限。这些数字是特定夹具结果，不是所有人物卡的性能结论。最终 commit 的局部耗时不能代表整轮体验。

已经确认的结构性开销：

- journal 冷读取先 materialize 完整快照，普通 read 再深复制整个 Chat。
- 首次视图有消息窗口，但随后自动补齐全部 Helper 历史。
- 模板过期版本写入可能恢复旧 Chat，进行全量三方合并。
- 前台消息追加仍将完整变量复制到消息上；回滚可通过旧 storage revision 恢复完整 Chat。

因此先重构数据所有权、读取粒度与提交单元，再选择文件、分块索引或数据库实现。仅把完整 Chat JSON 放入数据库，不满足本设计。

## 保留的领域语义

沿用 [CONTEXT.md](../../CONTEXT.md) 的 Story Timeline 权威性：

1. Foreground Turn 是独立提交边界。正文成功即可显示，后台结算失败不撤销正文，也不永久阻止下一轮。
2. 迟到后台结果必须检查所依据的剧情、状态和执行生命周期；不能覆盖较新的剧情。
3. Last Round Replacement 保留原输入，只替换最后一轮；前台成功后即保留新正文。内部内容版本不意味着新增多 Swipe 切换产品功能。
4. Failed Turn Replay 不制造已提交 Round，不改变原输入和模型请求前缀。
5. MVU submission、prepared effect 与最终回执可恢复；宿主变量提交去重不等于任意脚本外部副作用 exactly-once。
6. 原生 Session 和浏览器都是投影，但现有回滚、替代与后台 Agent 恢复必须继续协调，不能只切 Tavern 指针就宣告完成。
7. 完整历史读取仍返回隔离的数据；不能将部分 Chat 冒充完整 Chat，不能将未加载历史返回成不存在。

## 数据模型

下列结构是逻辑记录，不预设数据库表，也不要求一个记录对应一个文件。记录之间通过稳定 ID 关联，不通过嵌套整个对象关联。

### ConversationHead：会话当前入口

```text
id, schemaVersion
cardRef, settingsRef
activeBranchId, activeCommitId
currentStateId
historyRootId, tailPosition, messageCount
activeOperationRefs
headRevision
```

Head 不包含 messages、所有任务、全部请求去重记录或无限增长的楼层映射。数量、尾部位置和当前待办是提交时维护的索引，不在打开时扫描历史计算。设置可独立版本化；回滚剧情不应撤销期间保存的非剧情设置。

### Message 与 ContentVersion：内容及身份

```text
Message: id, turnId, role, createdAt, contentVersionId
ContentVersion: id, messageId, sourceText, canonicalText, attachments
```

消息 ID 稳定，楼号由当前分支的历史顺序决定，不以数组下标作为全局身份。内容修订产生新版本；被引用的旧内容保留。展示 HTML 不与权威正文混存。导入来源、原生消息映射和历史版本作为关联记录，不扩大 Head。

### HistoryIndex：可分页历史顺序

按分支和位置查找消息引用，提供尾部页、游标前页和指定位置查询。分支可以共享已提交前缀，但必须有可寻址索引；不能只靠从头遍历的父节点链，也不能在每次追加时复制全量 ID 数组。

分页游标绑定分支及历史版本。回滚或替代后旧游标应明确失效或继续读取其固定快照，不能混合两条历史。前端只保存已加载页面，不创建 N 个占位元素，也不无条件补齐未加载页。

### StateVersion：状态与历史状态

逻辑状态包含变量作用域、姿势、剧本进度等权威游戏数据；全局变量和宿主环境仍有各自所有权与版本，不能错误并入会话私有状态。

```text
StateVersion: id, parentStateId, checkpointRef / deltaRef, schemaVersion
CurrentState: 可直接读取的当前状态表示，与 currentStateId 一致
```

当前状态必须可直接读取，不从第一轮重放。历史采用检查点加增量，按增量条数及累计字节限制恢复成本；具体阈值由原型测量确定。未变化的数据可以由不可变数据块共享，但第一阶段不强制实现复杂的持久化树。

消息、内容版本和状态的对应关系独立记录：`messageId + contentVersionId → stateBeforeId / stateAfterId`。未结算回复可以没有 after；多条消息可以引用同一状态。MVU 重算始终使用相应正文的结算前基线，而不是直接对已结算结果再次执行。

历史变量编辑产生新的关联版本；是否允许某类旧消息编辑、是否影响当前状态，沿用现有接口语义逐项映射，不能隐式重算后续万轮。

### StoryCommit 与 Branch：剧情位置

```text
StoryCommit:
  id, branchId, previousCommitId, turnId
  historyRootId, messageRange
  stateBeforeId, operationRefs, nativeProjectionRef
Branch: id, parentBranchId, forkCommitId
```

Foreground commit 建立剧情事实；随后结算通过独立记录绑定该正文和 stateAfterId，不伪造第二个 Foreground Turn。分支与状态历史保留旧引用，回滚选择相应剧情位置及状态。待办操作作废和原生投影恢复属于同一业务流程。

### Operation 与 Delivery：可恢复执行

```text
id, kind, targetCommitId, targetContentVersionId
basedOnStateId, lifecycleVersion
status, submissionRef, preparedEffectRef, receiptRef
idempotencyKey
```

任务、租约、回执和去重记录按 ID 查询，待办索引支持重启恢复。活动状态由 Operation 派生，避免多个独立可写状态源。已完成记录独立归档，不能全部堆入 Head。去重保留期与恢复能力一起设计，不能为了裁剪记录破坏重复提交防护。

### DisplayArtifact 与 ExecutionResult：展示与副作用

DisplayArtifact 以消息内容版本、模板版本及已知依赖版本关联结果。只有依赖确实匹配才复用；未知依赖保守失效。普通历史展示按可见窗口处理，历史修复不能成为新一轮的全量前置步骤。

EJS/Helper 可能修改变量：这类执行结果及执行标识是持久事实，不能当作可丢弃 HTML 缓存。缓存丢失不应重复执行扣钱、发物品等副作用。纯展示重建与带副作用执行必须区分；迁移无法证明安全时保留旧执行路径，不自动重放。

## Module 与 Interface

由 Conversation State Module 集中索引、状态恢复、并发校验及提交规则。业务调用者使用意图明确的 Interface，不自行拼装存储操作：

```text
openConversation(id, pageSize)
readHistoryPage(id, cursor, pageSize)
readMessageState(id, messageId, contentVersionId)
commitForeground(id, expectedBasis, input, reply, operationId)
commitSettlement(id, expectedBasis, preparedEffect, operationId)
restoreStoryPosition(id, expectedBasis, target)
```

返回值只包含当前状态、请求窗口或实际变更以及版本凭据，不返回整份 Chat。完整导出和旧脚本兼容通过显式完整读取入口执行。底层 Adapter 如何寻址和提交是内部细节，业务接口不能要求先 readAll 再 slice。

## 提交流程与一致性

### 打开

在一致的读取版本下取得 Head、当前状态和尾部页面。显示当前内容后，只有用户翻页或明确的消费者请求才加载更多历史。模型上下文按已有上下文/摘要规则获取，不能因为界面只显示 50 条就擅自截短模型输入。

### 正文提交

校验操作基线，原子追加本轮消息和历史索引、保存结算前状态关联、建立 StoryCommit 与待结算任务、更新 Head。状态结算后续独立进行；正文不等待历史展示补处理。

### 结算提交

先持久化 submission / prepared effect；最终提交校验 branch、剧情位置、状态版本、目标正文版本与生命周期。原子写入新的状态、正文状态关联、任务回执及 Head 指向。重复操作返回原回执，冲突返回明确的过期或可重试结果。

一个全局变更序号可以用于通知排序，但不能成为所有无关记录的唯一冲突依据。显示缓存更新不应让 MVU 进入整档合并；相同变量或剧情依赖冲突仍必须检查。

通知在持久提交后发出，消费者通过版本补齐所需范围；丢失通知不丢失权威结果。跨原生 Session 或其他存储不能假定原子性：同次领域提交保存待同步记录，由幂等执行器补完投影。恢复顺序必须保留现有替代正文和失败重放契约。

跨进程以及直接文件修改的版本发现不能被进程内缓存取代。模板逐条执行的外部状态可见性沿用 [模板投影设计中的约束](template-projection-state-sync.md)，不顺带改成整批固定快照。

## 性能契约

记 N 为历史总长度、W 为请求窗口、V 为当前状态大小、Δ 为实际修改量。目标是普通打开和继续游玩不做 O(N) 的复制、扫描、序列化或通信；不是承诺任意状态/脚本都严格 O(1)。索引查询可有 O(log N) 成本。

| 场景 | 允许参与的数据 |
| --- | --- |
| 首屏 | Head、当前状态、W 条消息及必要显示结果 |
| 正常追加 | 本轮消息、必要上下文、索引增量 |
| MVU 结算 | 当前状态或受影响部分、Δ、目标消息与任务 |
| 历史分页 | 指定页及有限索引路径 |
| 历史变量/回滚 | 目标检查点及有上限的增量恢复 |
| 导出/显式全历史脚本 | 允许全量，必须可识别、独立计量 |

同步访问完整 chat 的旧脚本无法无条件获得与 N 无关的性能。完整基线仅在兼容路径需要时构造，并明确等待完成；不能用空数组、异步占位或未标注的不完整视图替代原语义。需要在接入前列出 Helper、EJS、MVU 各个入口的实际读取范围。

清理旧版本只能回收没有被分支、回滚、待办任务、历史状态及导出读取引用的数据。空间回收和检查点维护独立调度，限制单批工作量，避免每轮完整压缩。热缓存必须有按字节预算和失效规则，不能靠永久保留万轮对象掩盖冷打开成本。

## 实施阶段与决策门槛

1. **读取清单与度量**：列出首屏、正文准备、提交、模板、MVU、原生 Session、回滚的完整读取调用；记录读取行数、复制/传输字节和各阶段耗时。建立 1000/10000 轮同结构夹具。
2. **接口与逻辑模型原型**：先验证 Head、状态引用、历史页、追加/结算的提交规则。旧存储 Adapter 可用于验证行为，但其内部仍全量恢复时不得宣称性能完成。
3. **可寻址持久化**：对比索引分块文件与数据库 Adapter，验证冷读、原子提交、跨进程和目标平台可用性后再决定。必须能不恢复完整快照就读取最后一页。
4. **关键路径接入**：先首屏和本轮正文/MVU，再模板与原生 Session 投影。UI 不自动全量 hydration；保留可观测的显式兼容恢复。
5. **迁移与发布验证**：通过下述行为、崩溃与性能验收后再切换默认存储。每阶段独立提交，禁止用超时放宽替代验收。

这是数据结构与访问方式重构，不新增任意历史编辑、多 Swipe 产品能力，也不改变提示词顺序、模型工具定义和缓存前缀。

## 旧档迁移

迁移允许一次 O(N) 处理，但要单独计时，不能把迁移耗时当作新格式正常打开。使用临时目标及进度标记，可中断恢复；验证消息顺序、正文、变量基线、任务回执、回滚位置和原生映射后，才原子切换权威入口。原文件保留。

迁移期间冻结或可靠协调源写入，并验证源版本未变化；不能一边复制一边漏掉新结算。生产切换后旧副本只是迁移前备份，不能当作含有后续新数据的即时降级方案。先明确反向导出/恢复能力，再承诺版本回退。

不长期维护两个可独立写入的权威存储。旧字段的无损承接清单须包含插件自定义数据、消息变量、mvuBaseline、模板标记、脚本作用域和 pending delivery；无法解释的数据保留并阻止有损切换。

## 验收

- 行为：普通游玩、重算、结算失败后继续、跨页面同步、重启恢复、回滚及撤销、最后一轮替代、失败重放、历史变量访问与完整导出。
- 模板：旧展示修复、外部状态刷新、脚本历史读取、变量副作用不重复。
- 并发/崩溃：每个提交阶段中断恢复；重复和迟到回执；多页面/多进程竞争；通知丢失；原生投影尚未完成时重启。
- 操作量：固定 W 和 V 时，1000 与 10000 轮首屏读取行数及正文传输量相近；普通追加和结算不得遍历历史或恢复完整旧 Chat。禁止用只测最后 journal append 的指标通过。
- 时间：分开记录迁移、运行时启动、首屏正文、状态栏就绪、发送至变量提交、提交至持久化、持久化至可见；连续多轮报告分布和超时，不只报告最快样本。
- 数据：当前状态与历史还原一致；分支共享不串改；消息 ID/楼号映射正确；新写入独立落盘读取可验证；迁移前后导出的语义内容一致。

具体毫秒门槛在同一环境的原型测量后设定。首个不可放宽的门槛是消除普通路径对全量历史的隐式依赖。
