# 长档追加与 MVU 增量优化

## 改动

1. 日志缓存记录最早发生布局变化的消息位置。跨多个 revision 合并证据时保留最小位置；旧楼替换、轮次变化、截断后增长不能冒充纯追加。缓存失效或证据缺失仍回退。
2. Helper 投影遇到已验证的尾部追加时，只投影新增/变更楼层，复用历史消息索引，并增量更新不可变轮次映射。
3. MVU 派发支持追加楼层和轮次映射增量。仅新客户端声明 `appendContextVersion=1` 时启用；旧客户端仍用完整上下文。
4. 修复冷加载占位基线的同步遗漏：存储的 dirty indices 不能证明客户端已补齐历史。占位视图过渡到完整视图时重新比较历史，之后恢复普通增量。
5. 修复派发与页面同步的时序冲突：客户端若已同步到任务的精确目标 revision，可直接应用任务增量；过新、过旧、生命周期不匹配或已有事务仍拒绝。

这些改动保持同步历史读取、变量事务隔离和版本校验。没有取消旧卡历史补齐，也没有改动磁盘快照格式。

## 验证方法

- Helper 回归以 1000、10000 条源消息验证：追加两条时只读取新增两条，旧楼引用保留，轮次映射与完整投影一致，旧映射不可被后续追加修改。
- 存储回归覆盖跨 35 次写入合并证据、旧轮次修改、截断后增长。
- 真实 journal + adapter + dispatch + iframe 协议回归覆盖追加派发、历史变量修改、CAS 冲突、持久化、旧客户端回退、历史同步读取和目标 revision 抢先到达。
- 冷窗口同步回归先复现“旧楼保持 stub，但 messagesPending 已删除”，修正后完整视图恢复一致。
- 浏览器 E2E 使用隔离 Profile、官方 MVU 和固定模型。在 1000 轮、1999 条消息、约 47.6MB 逻辑 JSON 的存档中实际继续游玩，逐次独立读档校验金币、全部合成字段及完成回执。与旧的“重新结算”数据分开统计。

## 局部操作量

| 追加一条消息 | 优化前读取楼数 | 优化后读取楼数 |
| --- | ---: | ---: |
| 1000 条历史 | 1001 | 1 |
| 10000 条历史 | 10001 | 1 |

局部单次微基准从 3.96 / 25.49ms 变为 0.19 / 0.16ms，仅代表 Helper 投影，不是整个游玩流程的加速倍数。操作计数是更可靠的证据。

## 仍存在的工作

冷打开仍需恢复完整磁盘快照，旧脚本历史仍会主动补齐；超出整档缓存预算后的退化尚未改变。浏览器新增楼层时的部分完整上下文刷新也仍可优化。因此本次不声称整个万轮游玩已经达到 O(1)，也不声称已完成万轮浏览器 E2E。

对照 `run-QioSND` 已含本轮早期的追加投影改动，但尚未修复冷占位同步和版本竞态，因此不是前一个 Git commit 的完整 A/B 基准。数据说明这些同步回退被消除后的效果，不能推出所有人物卡都有固定加速倍数。每组只有 3 个样本，不报告 p95。

中间版本 `run-SuuYW9` 已能派发 2 条，但每次又请求完整恢复；最终 `run-nRtio6` 三次事件记录都只有一次 compact=true 的派发，分别覆盖总消息数 2001、2003、2005。逐次核对落盘金币、20 个合成字段、回执 updated、pending=false。

这些时间从模型更新进入结算开始，不含生成正文和模型思考，也不是从点击发送算起。日志 append 完成不等于 fsync；状态栏时间为 DOM 更新后两次 requestAnimationFrame。原始时间戳、回退证据和阶段事件见 [测量数据](long-archive-append-optimization-20260927.json)。
