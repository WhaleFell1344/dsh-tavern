# 长档优化空间核查

本次只做代码核查和局部探针，未修改生产逻辑。沿用上一轮完整 E2E 的计时，不把下述微基准当作整轮耗时或已实现的提速。

## 1. 新增楼层没有完整走增量路径（优先）

`tavern-helper-context.js:121` 的 indexedReuse 要求消息长度不变、layoutChanged=false。追加一楼时，即使已有全部旧投影，仍遍历所有楼层、重建 turnMessageIds 和索引；旧变量投影可复用，并非每次深拷贝所有变量。

`tavern-script-host-adapter.js:734-744` 的执行上下文也要求浏览器基线完整、版本匹配且变更 layoutChanged=false 才选取少数楼层；追加导致布局变化时会走完整上下文。是否在某一次 E2E 中发生仍需记录实际分支，不能仅凭代码断言它解释了全部延迟。

局部探针直接调用生产 projectTavernHelperContext；Proxy 统计源消息索引读取，包装 structuredClone 统计调用。每楼带约 2KB 字符串变量。单次计时仅供定位，操作计数更有意义：

| 操作 | 1000 条源消息 | 10000 条源消息 |
| --- | ---: | ---: |
| 冷窗口 48 条：读取源楼数 | 1000 | 10000 |
| 补齐旧历史：读取源楼数 | 952 | 9952 |
| 修改末楼：读取源楼数 | 1 | 1 |
| 追加一楼：读取源楼数 | 1001 | 10001 |
| 修改末楼：clone 调用 | 7 | 7 |
| 追加一楼：clone 调用 | 7 | 7 |

万条源消息时，单楼修改 0.07ms、追加一楼 25.49ms、完整投影 78.20ms。此处只测 Helper 投影，不包括存储、RPC、浏览器或 MVU。源消息数不等于游玩轮数。

优化方向：区分纯尾部追加与删除、插入、替换布局；对纯追加复用旧索引分支、增量追加 turn 映射，并让执行上下文协议携带新消息数量和新增楼层。不能简单删除长度校验，否则可能漏掉映射更新或错误接受旧基线。

## 2. 冷窗口只是分两次全量加载（优先）

`main.js:346` 将整个 messagesPending 范围请求给 hydrateTavernHelperMessages；`live-tavern-view.js:162` 在首包发布后立即执行它。服务端 `index.js:3464` 先 chatForSession，再投影请求范围，仍会获取可编辑的完整 Chat。

`session-view-reader.js:78` 不缓存带 messagesPending 的视图。客户端补齐不等于服务端缓存也被补齐，下一次服务端读取仍可能需要完整读取与投影。现有单测明确覆盖“冷窗口后再完整构建一次”的行为。

优化方向分两层：

- 先避免冷窗口、补齐和完整投影间的重复读取，补齐接口使用指定范围投影，并维护版本一致的服务端缓存。
- 真正只加载最近窗口，需要按需读取历史的协议。当前 getChatMessages 是同步读本地状态，不能直接删除全量补齐而让旧脚本读到空消息；需明确脚本所需范围、准备阶段或兼容回退。官方 MVU 的常用最新楼路径可以先单独验证，不必让所有脚本同时迁移。

## 3. 超预算存档失去缓存及增量证据（优先查运行时命中）

`chat-journal-store.js:134,189-200`：默认缓存预算 256MiB，按对象与字符串估算内存，超过预算的单个状态不保留缓存。这不是磁盘 JSON 字节数阈值。

`cachedState()` 未命中会 materialize 全档；`readSlice()` 也先走它。`readChangedSlice()` 依赖缓存中的变更证据，因此超预算可能同时使视图和执行上下文退回完整路径。现有 oversized-state 单测验证：连续读取小切片会重复解析全档，而且增量证据缺失。

没有测得上一轮特定 E2E 样本的缓存估算值，不能断言那些样本已越过 256MiB。下一步应记录缓存命中、估算字节、驱逐原因和全量回退次数，与慢请求时间对应。

优化方向：将轻量版本/变更索引与大正文缓存分开预算，进一步按历史块缓存。直接扩大整档缓存只推迟阈值，不能解决万轮增长问题。

## 4. 真正的磁盘分页需要改变快照组织

目前 readSlice 是内存切片接口，不是磁盘随机读取接口。冷态先解压、解析整份 snapshot，再重放 journal。另有默认 256MiB 的 snapshot 大小上限（独立于缓存预算），写快照和读取 gzip 快照都受限，因此无限增长的单文件快照不适合作为万轮保证。

方向：可直接读取的会话头与最新变量、分块历史、楼层/轮次索引、增量日志。需要保留旧档读取与迁移、修订一致性、回退和崩溃恢复契约；这是独立存储改造，不应混进一个小性能补丁。

## 建议验证顺序

1. 在现有 E2E 加入全量/增量分支、缓存失效和 payload 字节计数，确认慢样本实际走哪条路径。
2. 先支持纯 append 的 Helper 投影及执行上下文增量；验证 1000、10000 条历史下旧楼访问量不随历史增长，同时覆盖回退、重新结算、跨页面和脚本历史读取。
3. 处理冷加载重复补齐和超预算时的增量退化。
4. 独立设计分块存储，使冷打开也不再全量恢复。
