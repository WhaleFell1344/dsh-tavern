# 长档前台准备与并发冷读优化

本轮目标是减少前台的全历史操作，保留完整 Chat API 的深拷贝隔离和现有存档语义。万轮功能测试通过不等于性能达标；以下时间包含固定模型、真实隔离 DSH、Chromium、官方 MVU 和独立磁盘读取校验，不包含真实模型推理延迟。

## 已实现

1. 前台准备阶段只保存输入、世界书、运行状态等元数据。使用捕获的元数据基线与当前版本三方合并，再做带版本校验的 journal patch。并发历史更新通过变更切片刷新到调用者的草稿后，才提升草稿版本；缺少变更证据时回退读取当前完整历史，不恢复旧版本整档。冲突检测、字段删除、并发追加和截断保留。
2. 开始正文任务只对元数据执行时间线转换，沿用本次读取已隔离的历史数组，避免再做一次全历史 JSON 复制。普通 timeline.apply 和完整 Chat 读写的隔离语义不变。
3. 同一会话、版本、资源版本和窗口参数的并发视图请求共享读取与投影。不同版本或窗口参数仍分别处理，旧请求不能覆盖新缓存。

操作量回归使用 20000 条历史消息，禁止字段保存调用完整 read/update/readRevision，并验证并发历史修改保留、未变更行对象不被复制。正文准备测试用历史正文 getter 阻止遍历，修改前在 timeline.ensure 的 JSON.stringify 失败，修改后通过。12 个同时冷读请求从 12 次完整读取/投影降为各 1 次。

## 夹具边界

新增 `TAVERN_PERF_HISTORY_READY=1`：先让真实模板引擎为原始正文生成显示标记，再复制相同正文。此前夹具替换了正文但保留旧标记，会制造全历史显示补处理。这两个场景应分别保留；本轮没有用新夹具与旧夹具作速度倍率比较。合成重复正文也不代表所有复杂人物卡。

配置：`TAVERN_PERF_FIELDS=2 TAVERN_PERF_BODY_REPEATS=10 TAVERN_PERF_HISTORY_READY=1 TAVERN_PERF_APPEND=1`；严格增量断言保持开启，未增加 120 秒的界面等待上限。1000/10000 轮分别为 1999/19999 条历史消息，金币加两个合成字段。

## 下一阶段设计边界

当前 journal 的 cold materialize 仍读取完整快照；普通 read 随后复制整个 Chat。前台正文提交、模板过期版本合并和部分后台准备仍可能进入这些路径。只让可见界面显示最近 100 轮，并不能让底层读取成本自动变成常数。

进一步实现万轮快速打开，需要评审两项较大的改造：

- 把内部继续游玩路径统一为元数据、明确楼层切片和追加事务，旧版本合并按字段/楼层取证，避免恢复整个旧 Chat。外部完整读取和导出保持兼容。
- 将历史按块持久化，独立存储头部和索引，使打开先取最近窗口；模板补处理按块排队并让出前台。同步读取全历史的 Helper 脚本仍需完整基线，因此必须明确兼容路径，不能伪造空历史来追求速度。旧存档迁移要保留恢复路径。

建议按上述顺序实施：先在不改变存储格式的条件下消除每轮全量内部事务，再引入分块冷读。仅扩大缓存或只缩小可见消息列表，无法覆盖已经确认的复制/恢复路径，不作为最终方案。验收应同时包含 1000/10000 轮同结构档案、连续多轮、跨页面变量同步、刷新/重启、回滚、旧档显示补处理及完整历史脚本；使用操作量断言确保普通追加不扫描全历史，并分别报告冷打开、前台准备、变量提交至落盘和落盘至可见时间。

本轮没有擅自改变存储格式或截断历史 API。
