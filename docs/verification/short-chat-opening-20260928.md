# 短存档打开时重复读取大体积快照

2026-09-28，当前分支 `codex/current-state-paged-history`。

## 实际问题与定位

用户报告「创世回廊5.3 / 游戏人生深渊开局初始化」刚开局也打开很慢。通过本地宿主投影中的标题核对，目标存档有 5 条消息，已是原生分页格式。人物卡快照约 8.34 MB，开局世界书快照约 7.94 MB。不是历史轮数多造成的读取量。

现有服务的 Chromium 自动化从启动点击操作到状态面板出现两次分别约 5.3/7.3 秒，iframe 元素出现约 5.4/7.5 秒；此数字包含浏览器自动化等待点击条件的时间，不等于全部脚本已就绪。打开期间多次 getSession 请求耗时约 2～6.5 秒。服务分段诊断显示，视图缓存命中时 readOpeningWindow 仍消耗约 0.6 秒，并发期间达到约 2.1 秒。

原因：getSession 先尝试 readOpeningWindow；底层先 materialize 人物卡、世界书和消息，返回后上层才检查 from === 0、发现短存档无需分页，放弃窗口并继续普通视图路径。这项工作发生在视图缓存判断之前。

## 改动

readWindow 增加可选 requirePartial，仅由打开窗口的尝试路径启用。根据同一 pinned revision 的消息数量判断 from === 0 后直接返回 null，不加载快照。默认窗口读取、完整读取、长存档分页、旧 revision 与原存档均保持原行为；未修改 DSH 本体。

## 验证与边界

- 回归用大体积卡片 + 2 条消息重现：修改前失败，修改后通过。验证提前返回、读取字节限制、默认完整窗口和真正的分页窗口。
- native-conversation-storage 与 session-view-reader：39/39 通过。
- 同一真实存档三个独立 storage reader 的只读比较：原路径 562/512/489 ms，均读取 16,961,418 bytes；提前判断路径均不足 1 ms，仅读取 1,112 bytes。
- 以上是被修复环节的实测，不能将其当作整页 E2E 改善。运行中的用户服务未重启，修复后整页耗时尚未测量。并发会话请求、前端与人物卡脚本加载仍可能有额外成本。
- 调试脚本和含私人数据的诊断存放于 ignored 的 output/opening-real，不提交存档或日志。
