# 万轮继续游玩：第二轮优化与验证

本轮没有证明“万轮下整轮也很快”。已经修复两个随历史增长的显示/传输开销，万轮测试又暴露出前台整档读写和 MVU 全量恢复。以下区分操作量回归、完整浏览器流程和诊断采样，不能把最后一次 journal append 的速度当作整轮速度。

## 改动

- 浏览器父页面向 Helper iframe 同步纯尾部追加时，使用带 messageCount 的 committed delta。旧楼层沿用不可变索引，不再因为数组长度增加而复制和发送整个上下文。缺少新增行、长度缩短、生命周期变化仍恢复完整基线；不改旧 committed delta 的默认长度。
- 模板宿主的隐藏格式化 DOM 只挂载最近 200 条消息，加上当前历史渲染批次明确指定的楼层。完整 chat 数组、楼号和变量保留；历史批次仍能渲染自身楼层。插入使用一次集合快照与 DocumentFragment，避免逐条读取不断失效的 live HTMLCollection。关闭渲染时不为 pending 全历史构造 DOM。
- 性能夹具支持 10000 轮、可配置正文长度，记录发送至变量提交/可见的时间，增加超出缓存预算的诊断日志。默认仍要求增量派发；TAVERN_PERF_REQUIRE_COMPACT=0 仅用于保留全量回退时的诊断样本，不能作为增量验收通过的依据。

兼容边界：完整聊天 API 的历史读取没有截断；隐藏 `.mes` DOM 改为窗口，任意远古节点不再常驻。直接遍历隐藏 DOM 的自定义模板可能看到窗口范围，应通过 chat 数据读取任意历史。可见聊天、存档格式和变量内容没有因此删减。

## 操作量与行为回归

`mvu-view-refresh-cost` 在 20、400、10000 条消息下追加一条，断言真实父页面发送 committed delta，只有一条新增消息，并由生成的 iframe runtime 应用；旧变量保留。修改前这三个大小均因发送完整 context 失败。另覆盖缺失尾部与截断拒绝。

`template-mirror-cost` 使用 20000 条消息，普通镜像为 200 个节点；处理第 0、1 楼时为 202 个节点。追加、编辑、截断和节点复用均核对，完整源数组保持 20000/20001 条。真实模板子进程回归验证：输入表达式仍能访问窗口外第 0 楼的变量，以及完整 chat 长度。

## 万轮实测中的失败证据

真实隔离 DSH、Chromium、官方 MVU、原生 Session 和 journal；固定模型，历史为合成数据。10000 轮对应 19999 条消息，继续一轮应追加 user/assistant 两条。新建夹具后重启的时间包含历史构造、旧 Session 格式迁移、冷打开与等待状态栏，不能标为纯磁盘加载耗时。

- `run-Bo5EdE`：84,711,419 字节 JSON，3 个 stat_data 字段，正文重复 10 次。已打开，继续游玩等待 120 秒超时；服务端模板执行超时。此时已有 iframe 增量改动，尚无 DOM 优化。
- `run-EYxsgI`：同尺寸，只做 DOM 批量插入仍未通过。证明单纯替换插入方式不足以解决全历史格式化。
- `run-b34Pui`：加入 DOM 窗口后，已越过模板阶段，日志出现 input、prepare-worldbook、prepare、foreground.commit；仍在 120 秒内未完成变量更新。不能宣称万轮流程已通过。
- `run-HWwtaZ`：将合成变量减少到金币一个字段，51,352,629 字节 JSON，估算 Chat 对象约 141,294,986 字节。实际完成落盘和界面更新，且独立新建 store 核对金币、消息数与 receipt；随后因全量派发 20001 条消息违反增量断言而失败。变量提交到 commit 返回约 **13.69 秒**。该轮含 5 秒 CPU 诊断采样，不作为无采样的速度基准。

以上均是需要保留的失败/诊断结果，不能仅因为有一次落盘就计为万轮性能通过。3 字段夹具也不等价于大型复杂人物卡，字段数以外还有 MVU schema、基线与脚本数据。

## 当前定位

在 `run-HWwtaZ` 前台准备期间采样服务端 5 秒：热点包括 jsonClone、copyJsonTree、structuredClone、diffJson、freezeJson 与垃圾回收。调用栈直接指向 chat-persistence.write / refreshDraft / mergeValue、chat-journal-store.update / readRevision 和 MVU 回执投影。说明耗时发生在末尾追加以外的整档准备、复制、旧版本合并和视图生成。

全量恢复的日志：浏览器拥有完整 20001 条消息、基线 revision 33；结算当前 revision 34，但 resolveChangedChatSlice 没拿到变更切片，于是退回完整上下文。这个样本没有 cache-oversized 日志，因此不能将其直接归因于 256MiB 预算。并发缓存失效、旧版本证据与投影条件需要继续追踪，尚无最终根因。

下一阶段应优先将前台准备的已知字段变化改为有版本校验的 scoped patch，减少整档 write 的复制/合并，并定位变更证据丢失。真正只从磁盘读取最近窗口，仍需要历史分块与索引；单文件快照的冷恢复不是 O(1)。不能通过增大超时或取消独立落盘校验来宣称完成。

## 无 CPU 采样的连续游玩复测

`run-PeIG1X`，10000 轮、19999 条消息、约 51.35 MB JSON，仅金币一个合成字段，正文重复 10 次。此诊断启用 `TAVERN_PERF_REQUIRE_COMPACT=0` 以记录回退样本；日志中两次实际均为 compact=true、派发 2 条。没有把关闭断言当成通过证明。

| 边界 | 第一轮 | 第二轮 |
| --- | ---: | ---: |
| 发送 → 变量提交 | 49.34 秒 | 109.85 秒 |
| 变量提交 → commit 返回 | 4.72 秒 | 6.49 秒 |
| commit 自身 | 117.7 ms | 139.3 ms |
| 发送 → 状态栏可见 | 62.81 秒 | 超过 120 秒等待上限 |

第一轮独立新建 store 核对持久化内容通过。第二轮 commit 时间来自服务端日志，界面超时导致独立 store 校验没有执行，不能计作完整 E2E 通过。整次运行状态仍是 failed。

夹具不是自然累积游玩的实录：历史正文被合成替换，部分复制的模板显示标记不再匹配新正文，重开后会发生历史模板补处理。原生 Session 也经过迁移。因此不能把上述耗时推广为所有真实万轮存档；它确实暴露了历史补处理与前台工作竞争时的整档复制成本。后续需要同时测显示缓存已就绪的热档与需要补处理的旧档，不能靠删掉后者来掩盖问题。
